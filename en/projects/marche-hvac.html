Anticipating the heat pump market, department by department

// In 30 seconds

The problem, the answer, the proof

For an HVAC distributor, knowing where and when the heat pump market will accelerate drives inventory, sales force and installer partnerships. The signals exist (energy performance diagnostics, building permits, weather, economic conditions) but are scattered.

The project brings them together every month in a reproducible pipeline and delivers a forecast per department.

For recruiters · business value
  • A topic chosen from my own industry: the variables (MaPrimeRénov', CEE, housing type) come from field knowledge.
  • Honesty about results: I audited my own project, found target leakage that inflated the scores, and republished more modest but true figures.
  • A deliverable a sales leadership team can use: map of France, forecasts, comparison with a naive forecast.
  • Documented governance (GDPR, AI Act).
For tech teams · what the code proves
  • Collectors built on a plugin architecture (BaseCollector + registry), no API key required.
  • SQLAlchemy star schema (SQLite, PostgreSQL 16 or SQL Server), outlier detection with IQR / Z-score / Isolation Forest.
  • Temporal train / validation / test split, TimeSeriesSplit on date-sorted rows, rolling features shifted by one month, anti-leakage tests.
  • Benchmark against two naive forecasts (persistence and seasonal); SHAP explainability.
  • FastAPI with 6 endpoints, 6-page Streamlit app, multi-stage non-root Docker, monthly Airflow DAG and an equivalent Kubernetes CronJob.
  • CI: pytest 3.11 / 3.12 with coverage, ruff (46 errors fixed), Docker build + smoke test.

// Audit

What I fixed: target leakage

The originally published scores (Ridge: R² 0.9996, RMSE 9.2) were wrong. I reproduced them exactly, then found the cause: some features already contained the value to predict. Here is what was fixed, and what the models are really worth.

1 · The leak
  • Rolling means and standard deviations computed including the month to predict.
  • lag_1m + diff_1m rebuilt the target exactly: Ridge found the sum, hence R² 0.9996.
  • Cross-validation split departments, not time (the dataset was sorted by department).
2 · The fix
  • Windows, diff_1m and pct_1m computed on the series shifted by one month.
  • Rows sorted by date before TimeSeriesSplit.
  • 3 anti-leakage tests (they fail on the old code) and 1 on fold ordering.
3 · The real scores
  • Ridge over the 12 months of 2025: R² 0.968, RMSE 83.5.
  • −24.5% RMSE versus the “same as last month” persistence forecast, −21% versus the seasonal one.
  • LightGBM does not beat persistence on RMSE (+7.8%), only on MAE.

The same audit fixed 5 failing tests, 46 ruff errors that would have blocked CI, a SHAP crash (94 columns supplied versus 92 learned) and 2 defects in the Kubernetes manifests (dashboard namespace and volume).

Step by step

  1. On the 1st of each month, Airflow (or the Kubernetes CronJob) runs the collectors across the 96 departments.
  2. Raw data is cleaned, merged and loaded into a star schema; outliers are detected with three methods.
  3. Feature engineering produces lags, rolling means and rolling standard deviations over 3 and 6 months, computed on the series shifted by one month so they never see the month to predict.
  4. Five model families are trained on a temporal split (train ≤ June 2024, validation H2 2024, test 2025 → February 2026), compared with two naive forecasts, then explained with SHAP.
  5. Models are served by FastAPI and visualized in a Streamlit dashboard (map of France, forecasts, comparison with naive forecasts).

src/processing/feature_engineering.py — rolling windows shifted by one month (leakage fix)

                mean_name = f"{col}_rmean_{window}m"
                df[mean_name] = df.groupby("dept")[col].transform(
                    lambda s: s.shift(1).rolling(window, min_periods=1).mean()

tests/test_processing/test_feature_engineering.py — the anti-leakage test: perturbing y(t) must not change month t's features

        perturbed_input.loc[mask, self.TARGET] += 1000
        perturbed = self._engineer(fe, perturbed_input)

        row = (base["dept"] == dept) & (base["date_id"] == month_t)
        derived = [
            c for c in base.columns
            if c.startswith(f"{self.TARGET}_")
        ]
        assert derived, "expected target-derived features"
        pd.testing.assert_frame_equal(
            base.loc[row, derived].reset_index(drop=True),
            perturbed.loc[row, derived].reset_index(drop=True),
        )

// Critical review

Known limitations and next steps

Documenting limitations honestly is part of the job: it lets a team make informed decisions.

  • Proxy: a DPE follows a sale or a rental, not an installation. The model forecasts heat pumps observed during diagnostics.
  • Simplified multi-month API forecast: beyond one month, only lag_1m is updated; other lags and windows are not recomputed. Identified, not fixed.
  • Incomplete last months: DPE records reach ADEME late (February 2026 only a quarter collected) and the pipeline does not yet filter unconsolidated months.
  • Non-deterministic LSTM, sequences built without breaks between departments: it does no better than an average.
  • ReadWriteOnce Kubernetes volume shared by the API (2 replicas), the dashboard and the CronJob: incompatible with a multi-node cluster.
  • Not verified during the audit: docker build, kubectl apply on a cluster, running the Airflow DAG, full collection of the 15.9 M DPE records. No validation yet on months after February 2026.
  • No MLflow tracking or drift monitoring: the next component to add.
