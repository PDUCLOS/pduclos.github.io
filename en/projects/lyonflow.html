LyonFlow — Lyon mobility predicted in real time

End-to-end MLOps platform running in production on a VPS: 9 open data sources, Medallion architecture on PostgreSQL/PostGIS, 27 Airflow DAGs, automatically retrained XGBoost models, multimodal pgRouting routing and a dashboard for 3 personas.

The problem, the answer, the proof

The Lyon Metropolitan Area publishes dozens of open data feeds (traffic counting loops, TCL bus positions, Vélo'v bike stations, weather, roadworks), but no tool cross-references them to help a commuter choose a transport mode, an operator run its network, or an elected official decide on an investment.

LyonFlow collects these feeds every 5 minutes, refines them through Bronze → Silver → Gold layers, predicts traffic and Vélo'v availability one hour ahead, recommends the best multimodal route and delivers it all in an application designed for three audiences.

For recruiters · business value
  • A product in production, not a notebook: available online, monitored, backed up every night.
  • Designed for 3 business users (commuter, TCL operator, elected official) — same logic as sales management: each decision-maker gets their own view.
  • Cross-referencing bus delays × congestion separates an operational problem from an infrastructure need (dedicated lane): a quantified argument for a budget decision.
  • Project carried out solo end to end: scoping, data, models, deployment, GDPR documentation.
For tech teams · what the code proves
  • Medallion Bronze/Silver/Gold on PostgreSQL 16 + PostGIS + pgRouting, parameterized SQL throughout, zero hard-coded credentials.
  • 27 Airflow DAGs (collection every 5 min → 6 h, transforms, ML, maintenance), MinIO S3 archiving.
  • MLflow registry (6 models, Production stage), XGBoost retraining every 30 min, custom PSI drift + Evidently reports.
  • GitHub Actions CI: ruff, mypy, bandit, pytest + coverage. Deployment via make deploy-vps / rollback-vps, 20 health checks.
  • Prometheus + Grafana + Alertmanager observability, Nginx as the only exposed entry point, Let's Encrypt TLS.

Step by step

  1. Collection — 9 open sources with no API key, Airflow DAGs scheduled from every 5 min (traffic, buses, Vélo'v) to every 6 h (weather alerts).
  2. Bronze — immutable raw JSONB storage: history can always be replayed.
  3. Silver — deduplication (DISTINCT ON), SIRI parsing, geographic reprojection (4326 / 2154), filtering of faulty sensors.
  4. Gold — ML features (lags, rolling averages, school calendar, weather) and business materialized views (bottlenecks, delays by road segment).
  5. Modeling — XGBoost speed H+1h (inference every 15 min), XGBoost Vélo'v H+1h, car routing with pgr_dijkstra on the OSM network with injected speeds.
  6. MLOps — MLflow tracking, continuous comparison with TomTom data, daily drift report, automatic retraining.
  7. Delivery — FastAPI API (prediction, recommendation, bottlenecks) and an 18-page / 59-widget Streamlit dashboard, with no simulated data at all.

The code that makes the difference

src/monitoring/psi.py — robust PSI drift, no heavy dependency

def _safe_psi_term(pct_ref: float, pct_curr: float, eps: float = 1e-6) -> float:
    """One term of the PSI sum, protected against log(0) and division by 0."""
    if pct_ref < eps and pct_curr < eps:
        return 0.0
    if pct_curr < eps:
        pct_curr = eps
    if pct_ref < eps:
        pct_ref = eps
    return (pct_curr - pct_ref) * np.log(pct_curr / pct_ref)

// Critical review

Known limitations and next steps

Documenting limitations honestly is part of the job: it lets a team make informed decisions.

  • Single server: no high availability. The Kubernetes target (EKS/GKE) exists on a dormant branch.
  • Bus delay prediction still in the analysis phase: SIRI data needs to accumulate before going to production.
  • Off-site backup: rclone configuration still to be finalized.
  • Databricks variant in progress: week 1 delivered (Unity Catalog, Bronze ingestion, DLT), MLflow / Model Serving / Genie to come.
