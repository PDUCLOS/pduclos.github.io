From lab to shop floor: detecting a failing bearing

Fault diagnosis on the 32 real bearings of the Paderborn test rig from 5 explainable vibration indicators, with a validation that never puts the same bearing in both training and test, and a quantified measurement of the gap between lab-made and real faults. The model is served by a FastAPI API, containerizable and deployable on Kubernetes.

The problem, the answer, the proof

Most predictive maintenance demos test a model on the same bearings it saw during training: the scores look great and don't hold up on the shop floor.

This project measures the lab / field gap, compares a vibration sensor with the motor current already available on every drive (no extra sensor needed) and favors indicators a maintenance manager can understand.

Measured result: trained on machined faults, the model misses about 1 real fault in 5, versus about 1 in 14 when it has seen real faults. And it does not clearly beat a simple kurtosis rule.

For tech teams · what the code proves
  • 5 time-domain indicators (RMS, peak-to-peak, crest factor, kurtosis, skewness); BPFO / BPFI / BSF / FTF fault frequencies computed from the geometry, envelope analysis still disabled.
  • StratifiedGroupKFold grouped by bearing and an assert_no_asset_leakage safeguard; artificial → real benchmark over 20 splits of the healthy bearings.
  • PostgreSQL / TimescaleDB (fallback without the extension), MLflow, dataset hash for traceability, Evidently drift.

  • CI: ruff (pinned rules), 223 tests, ML pipeline smoke test on 2 real bearings (K001, KA01).
  • Physical simulators, SimPy factory simulation and Asset Administration Shell export (Industry 4.0).

// Key result

Lab-made faults versus real faults

The project's question: does a model trained on faults machined in a lab recognize faults that developed in operation? Training on 12 bearings with artificial faults + 3 healthy (1,199 measurements), testing on 14 bearings with real faults + the 3 other healthy ones (1,360 measurements), repeated over the 20 possible 3 / 3 splits of the 6 healthy bearings. Control: same healthy bearings, real faults learned with grouped cross-validation.

Reading
  • Trained on machined faults, the model misses about 1 real fault in 5, versus about 1 in 14 when it has seen real faults.
  • Recognition of healthy bearings stays weak in both cases: there are only 6 healthy bearings.
  • Exploratory measurement, to be confirmed with envelope analysis.
A bias avoided
  • The existing split_artificial_to_real() function put all healthy bearings in training: the test set held a single class and macro F1 was meaningless.
  • The benchmark therefore splits healthy bearings between train and test, and calls assert_no_asset_leakage on every split.
// Takeover

What I verified, fixed and added

Before adding anything, I re-ran the existing code on the 2,560 official files (5.4 GB of archives, 22.4 GB extracted). Full ingestion in 473 s: 2,559 measurements kept, 1 unreadable file excluded and listed. The baselines are reproduced to the thousandth; vibration XGBoost gives 0.734 ± 0.206 versus 0.738 published, a gap about 50 times smaller than the standard deviation.

Tests and CI
  • Broken lint CI: ruff 0.16.5 enabled 67 extra rules; rule set pinned in pyproject.toml.
  • Two tests that tested nothing (result without assert, overly broad pytest.raises(Exception)).
  • An integration test that was always skipped now loads a real .mat file.
Running outside Docker
  • TimescaleDB is no longer mandatory: falls back to a regular table with a warning on PostgreSQL.
  • Dashboard: hard-coded MLflow address replaced by MLFLOW_TRACKING_URI (Alerts and Results tabs were empty otherwise).
  • Service: xgb.Booster instead of XGBClassifier, which required scikit-learn in the image.
Additions
  • FastAPI API + demo page, same indicator functions as in training, 9 tests.
  • Dockerfile.api, Kubernetes manifests (kustomize: local 6 objects, prod 8 objects).
  • Reproducible benchmark, architecture diagrams, showcase page and video. 223 tests passed, 0 failures.

Step by step

  1. Download of the 32 Paderborn archives (5.4 GB, 22.4 GB extracted), parsing of file names (bearing, operating condition, fault) and physical plausibility checks; 1 unreadable file excluded and listed.
  2. Full ingestion in 473 s: 2,559 measurements, 7,677 signals, 46,062 indicators, stored site → area → machine → asset → bearing.
  3. Computation of time-domain indicators and characteristic fault frequencies from the bearing geometry.
  4. Comparison of a threshold baseline and XGBoost, with cross-validation grouped by bearing (no bearing in both train and test).
  5. Artificial → real benchmark: training on machined faults, testing on real faults, healthy bearings spread over 20 splits.
  6. MLflow tracking (dataset hash, macro F1, balanced accuracy) and Evidently train / test drift report.
  7. Model export (29 bearings, 3 held out for the demo) and FastAPI service; image and Kubernetes manifests.
  8. Streamlit delivery: alerts, indicators, factory digital twin, glossary.

The code that makes the difference

src/data/splits.py — safeguard against train/test leakage

def assert_no_asset_leakage(
    train_df: pd.DataFrame, test_df: pd.DataFrame, asset_col: str = "asset_id"
) -> None:
    """Garde-fou : leve une erreur si un asset_id apparait dans train ET test."""
    leaked = set(train_df[asset_col]) & set(test_df[asset_col])
    if leaked:
        raise ValueError(f"Fuite de donnees : assets presents dans train ET test : {leaked}")

// Critical review

Known limitations and next steps

Documenting limitations honestly is part of the job: it lets a team make informed decisions.

  • A single test rig, a single bearing model (6203), 32 bearings of which 6 healthy: standard deviations of 0.10 to 0.21 on macro F1; no guarantee of transfer to another machine.
  • Time-domain indicators only: envelope analysis (BPFO / BPFI) stays disabled until band selection (kurtogram) is stable.
  • Mixed operating conditions: generalization to an unseen operating condition is not measured.
  • The artificial → real benchmark is exploratory; the full phase 3 awaits the kurtogram decision.
  • Not verified in this session: docker build / docker compose up, TimescaleDB hypertable, deployment to a real cluster, API memory in a container, GitHub Actions CI (verified locally).
