From lab to shop floor: detecting a failing bearing

Bearing fault detection on the Paderborn dataset (32 bearings, 4 operating conditions) using explainable physical features, with one key question: does a model trained on artificial faults hold up on real faults?

// In 30 seconds

The problem, the answer, the proof

Most predictive maintenance demos test a model on the same bearings it saw during training: the scores look great and don't hold up on the shop floor.

This project honestly measures the lab / field gap, compares a vibration sensor with the motor current already available on every drive (no extra sensor needed) and favors indicators a maintenance manager can understand.

For recruiters · business value
  • Real domain expertise (field deployments with IFM, Schaeffler, SKF) put to work for data.
  • Sensor cost / value reasoning: can we avoid instrumenting a machine?
  • Negative results published as they are: rigor comes before showcasing.
For tech teams · what the code proves
  • Physical features: RMS, kurtosis, crest factor and BPFO / BPFI / BSF / FTF fault frequencies computed from the geometry.
  • Splits by asset / condition / artificial→real, StratifiedGroupKFold and an assert_no_asset_leakage safeguard.
  • TimescaleDB (features hypertable), MLflow backed by PostgreSQL, dataset hash for traceability, Evidently drift.
  • CI: Python 3.11 / 3.12 matrix, “zero mock” audit, full ML pipeline on real data with MLflow artifacts.
  • Physical simulators, SimPy factory simulation and Asset Administration Shell export (Industry 4.0).

Step by step

  1. Download of the Paderborn signals, parsing of file names (bearing, operating condition, fault) and physical plausibility checks.
  2. Hierarchical storage site → area → machine → asset → bearing in TimescaleDB.
  3. Computation of time-domain indicators and characteristic fault frequencies from the bearing geometry.
  4. Comparison of a threshold baseline and XGBoost, with cross-validation grouped by asset (no bearing in both train and test).
  5. MLflow tracking (dataset hash, macro F1, balanced accuracy) and Evidently train / test drift report.
  6. Streamlit delivery: alerts, spectra, factory digital twin, glossary.

// Code excerpts

The code that makes the difference

src/features/fault_frequencies.py — bearing physics

def bpfo(n_balls, fr_hz, d_mm, big_d_mm, phi_deg=0.0):
    """Ball Pass Frequency Outer race - outer race fault."""
    return (n_balls / 2) * fr_hz * (1 - _geometry_factor(d_mm, big_d_mm, phi_deg))

src/data/splits.py — safeguard against train/test leakage

def assert_no_asset_leakage(train_df, test_df, asset_col="asset_id"):
    leaked = set(train_df[asset_col]) & set(test_df[asset_col])
    if leaked:
        raise ValueError(f"Fuite de donnees : assets presents dans train ET test : {leaked}")
// Critical review

Known limitations and next steps

Documenting limitations honestly is part of the job: it lets a team make informed decisions.

  • Phase 3 (artificial → real) not yet run: this is the measurement that will validate real-world value.
  • Envelope analysis / kurtogram disabled until it is stable.
  • No inference API: the current deliverable is the study and the dashboard.
