Carrier: three projects in parallel, three problems, all still in use

Data Analyst, 12 months at Carrier HVAC Europe, on an SAP S/4HANA scope of 12 sales entities. I ran three projects in parallel, each answering a different problem: 1. measure whether the 3 factories keep the date promised to the customer; 2. measure the real workload and response time of the master data service; 3. track and eliminate automatic item creation errors sent by ERCD.

The problem, the answer, the proof

Project 1 — OTD, factory lead times. An order goes through sales, finance, master data, the factory, customer service and transport; the factory can reschedule several times. The data existed in 12 SAP exports of 240 columns, on 12 SharePoint sites, with different formats and currencies. It had to become a reliable measure of the customer promise.

Project 2 — ServiceNow, master data tickets. Existing dashboards only counted closed tickets: tickets open for several months disappeared, and both workload and response rate were distorted.

Project 3 — ERCD, error Pareto. Mass uploads from the spare parts business generated item creation errors; they had to be classified, tracked over time, and new checks had to be addable without development.

For recruiters · business value
  • Three problems, three answers: run in parallel, all put into production and still in use after I left.
  • Project 1 · OTD: lead time split by actor, customer dissatisfaction measured against the initial acknowledged date.
  • Project 2 · ServiceNow: tickets counted in their creation month, not their closure month; half of my time.
  • Project 3 · ERCD: an evolving Pareto used as the basis for action plans with ERCD.
For tech teams · what the code proves
  • Project 1 · OTD: Power Automate (12 SharePoint → 1, up to date at 8 am), Power Query (240 → 80 typed columns, 1.5 GB reduced to 800 MB per cycle), reading the report's ABAP / SQL code, format and currency harmonization, TMDL model and DAX measures.
  • Project 2 · ServiceNow: daily ServiceNow ticket report (mailbox → SharePoint → Power BI), tracking of tickets open from month to month, typing by reason and origin, pickup, processing and closure times.
  • Project 3 · ERCD: M and DAX only; cross-tables by error type, Pareto prepared in the data, reference CSV mapping each check to its category.

Step by step

  1. Source — each entity generates a 240-column CSV report in SAP S/4HANA; acknowledged and modified dates (Dates 1, 2, 3) come from the factories through a gateway.
  2. Collection — Power Automate moves and files the 12 reports, stored on 12 SharePoint sites, in one place, then triggers the refresh, every day at a fixed time.
  3. Preparation — Power Query keeps the 80 useful columns and types each one explicitly to recover the file's real structure.
  4. Qualification — the report code gives the source and label of each column; export anomalies are documented and reported to IT.
  5. Harmonization — national formats aligned, currencies rebuilt, data organized by entity, factory, order and line.
  6. Management — Power BI model and DAX measures: OTD, reschedules, dissatisfaction, lead time per step, month slippage.
// Project 2 · ServiceNow

Project 2 · ServiceNow — the real workload of the master data service

Illustrative scenario, fictitious values.

The problem with tickets that overlap months

Problem: the figures of the Carrier SAS master data service were wrong. This project took half of my time. It measures the activity of the service, which creates and updates items in SAP S/4HANA: one team supervises, trains and solves complex cases; a specialized team handles requests as fast as possible.

Source. Every day, a ServiceNow report of all tickets assigned to the service, exported from a mailbox to a SharePoint site, then processed in Power BI: creation, pickup, processing, closure, reason, origin.

The problem. Existing dashboards only counted closed tickets. A ticket still open appeared nowhere; a ticket open for several months slipped from month to month, then was counted all at once in its creation or closure month, depending on the case. The service's workload and response rate were distorted. I analyzed how the services counted tickets, then the rule was reset: each ticket is counted in its creation month, not its closure month. The expected values are matched, and tickets still open stay visible from one month to the next instead of disappearing.

Ticket typePathWhat it shows
SimpleCorrect request: picked up, processed and closed in one go, closure almost right after processingThe most frequent case, the one to aim for: right request, fast processing
Round tripPoorly worded request, sent back to the requester, then taken up again by master dataMuch longer total time, caused by the form
Multiple exchangesSeveral returns before completion, sometimes over several monthsThe tickets that distorted the months

What it enables. Requests are typed by reason and origin. It shows which countries and entities struggle most to state their need in the item creation form, so where to train first to get simple tickets from the start. Dashboards track activity over time and check whether the actions taken reduce processing time and round trips.

// Project 3 · ERCD errors

Project 3 · ERCD — an evolving Pareto of item creation errors

Illustrative scenario, fictitious values.

Error Pareto: a new check fits in without development

Problem: errors in automatic item creation sent by ERCD, Carrier's spare parts business. ERCD pushes pre-filled forms to master data, which mass-loads them into SAP. A colleague had built an Excel file that detects, at every upload, non-compliant data against a list of predefined error types.

Constraint: M (Power Query) and DAX only. Power Query reads the check file and builds the cross-tables by error type. Power BI has no ready-made Pareto chart: the data must be prepared (ranking, cumulative total) to make it usable. A reference table, a plain CSV, maps each check to its category.

ChangeWhat it takesResult
New error checkAdd a line to the reference CSV, with its categoryAutomatic: the error shows up in the right place in the Paretos
New error categorySpecific development in the modelRare, since categories are stable

What it enables. Action plans with the ERCD team to eliminate some error types for good, and spotting, over a given period, a new error type as it appears, for example when the person generating the file does not know some subtleties.
