The problem, the answer, the proof

Certification case study inspired by Stripe, on synthetic data — not affiliated with the company.

A payment platform must block a fraudulent transaction before approving it, without slowing down the transactional database and without analytics blocking production. It must also comply with GDPR and PCI-DSS.

The answer: separate the workloads. PostgreSQL for transactions, Debezium + Kafka to stream changes, Redis for real-time features, MongoDB for logs, Snowflake for analytics — and a monitored model that retrains itself when reality changes.

For recruiters · business value
  • A high-stakes financial topic: every missed fraud costs money, every false positive blocks a customer.
  • Architecture choices justified and quantified, including cloud cost (FinOps): ~$3,100/month in production, brought down to ~$2,400 with the identified levers.
  • Compliance built in by design: no card numbers stored, SHA-256 fingerprints, limited log retention.
  • Real incidents documented and resolved — evidence of an operations mindset, not just development.
For tech teams · what the code proves
  • Debezium CDC on the PostgreSQL WAL → Kafka (KRaft), idempotent score write-back.
  • Redis feature store (1 h / 24 h velocity in sorted sets) and the same feature vector at training and inference: zero training/serving skew.
  • Leak-proof temporal split, XGBoost with scale_pos_weight, MLflow registry fraud-detector.
  • Evidently monitor: automatic retraining if drift > 0.3, recall < 0.7 or precision < 0.5, with a cooldown period.
  • CI that spins up the entire stack without mocks + audit notebook executed as a quality gate; Terraform AWS (3-AZ VPC, RDS, MSK, ElastiCache, ECS Fargate, MWAA).

Step by step

  1. A producer inserts synthetic transactions (5% injected fraud) into PostgreSQL 16, configured for logical replication.
  2. Debezium reads the WAL and publishes every change to Kafka (stripe.public.transactions).
  3. The scorer enriches each transaction with customer velocities stored in Redis, then scores it (rules or XGBoost): allow, review (≥ 0.60) or block (≥ 0.85).
  4. The score is written back idempotently to PostgreSQL; events and alerts go to Kafka, then MongoDB.
  5. Every 2 minutes, the monitor compares recent data to the reference (Evidently) and to the performance actually served; it retriggers training when needed.
  6. Every night, Airflow exports to the Snowflake star schema and refreshes the materialized views.
  7. The Streamlit dashboard (authenticated) shows KPIs, alerts, drift and a rules vs. model comparison.
// Key strengths

Key strengths of the solution

  1. 01

    Real time end to end: Debezium CDC → Kafka → scoring (sub-second target), score written back idempotently.

  2. 02

    Zero training / serving skew: Redis feature store and the same feature vector for training and inference.

  3. 03

    A self-monitoring model: automatic retraining on drift or a drop in recall / precision, with a cooldown period.

  4. 04

    Costed, compliant architecture: 9 AWS Terraform modules, FinOps ~$3,100 → ~$2,400/month, no card numbers stored.

ml/train_fraud_model.py — temporal split to prevent information leakage

def temporal_train_test_split(df, X, y, test_frac=0.2):
    """Train/test split in chronological order (not random).
    A random split would mix past/future velocity windows:
    the model would indirectly "see" future transactions."""
    n = len(df)
    cut = int(n * (1 - test_frac))
    return X[:cut], X[cut:], y[:cut], y[cut:]
// Critical review

Known limitations and next steps

Documenting limitations honestly is part of the job: it lets a team make informed decisions.

  • Flink replaced by an equivalent Python consumer (PyFlink does not compile on ARM64); the PyFlink job exists as an optional profile.
  • Snowflake run in dry-run mode for lack of an account; Terraform validated but never applied.
  • No promotion gate or automatic rollback in the MLflow registry yet.
  • Offline / online gap observed over one window (served precision 0.52): flagged by the audit notebook itself, a lead for calibration.
