ML santé publique · Projet d'équipe relancé en 2026

Estimer les urgences respiratoires de la semaine, et le mesurer honnêtement

Estimation hebdomadaire des passages aux urgences pour infections respiratoires aiguës, par département, à partir des recherches Google de symptômes, de la pollution, de la météo et de l'indice grippal. Projet d'équipe relancé en 2026 : mesuré sur 429 semaines de 2024, six défauts corrigés, API FastAPI validée, déployable sur Kubernetes.

// En 30 secondes

Le problème, la réponse, la preuve

Les épidémies respiratoires saturent les urgences chaque hiver, et les données hospitalières consolidées arrivent avec retard. L'objectif : estimer la charge de la semaine en cours à partir de signaux disponibles tout de suite (recherches de symptômes, pollution, météo, indice grippal).

Projet d'équipe de formation (M2i) à 4, relancé en 2026 : audit, mesure sur 2024 comparée à une référence naïve, corrections, nouvelle API et déploiement Kubernetes.

Pour le recruteur · valeur business
  • Honnêteté sur le résultat : comparé à « même valeur que la semaine précédente », le modèle seul fait légèrement moins bien sur 2024 (MAE 41,2 contre 39,5). C'est écrit, et la piste qui en découle aussi.
  • Reprise d'un projet existant : six défauts reproduits avant d'être corrigés, chacun couvert par un test ou une validation.
  • Travail en équipe de 4 sur un sujet d'intérêt public.
Pour l'équipe technique · ce que le code prouve
  • LightGBM (100 arbres) sur 24 variables : 12 symptômes Google Trends, CO, NO₂, O₃, PM2.5, SO₂, IQA, pression, T° max, indice grippal, département, année, semaine (week_cos).
  • Audit des pickles (pickletools), unpickler à liste blanche, export en texte LightGBM + JSON : plus aucun pickle chargé à l'exécution.
  • API FastAPI : schéma Pydantic (24 champs obligatoires, bornes physiques, champs inconnus refusés), lot de 1 à 1 000 lignes ; interface Flask d'origine montée sur / (a2wsgi).
  • Évaluation reproductible (scripts/evaluate.py) ; latence d'inférence 0,431 ms p50 par ligne, POST /api/predict 7,05 ms p50 de bout en bout.
  • Dockerfile python:3.12-slim non root, kustomize base + overlays local / cloud (HPA 2 → 6, NetworkPolicy, PDB).

predictira/data.py — la correction

def load_dataset(root: str | Path) -> pd.DataFrame:
    df = pd.read_csv(Path(root) / "df_Test_Indust.csv")
    # week_cos seul est ambigu : cos(2π·w/52) = cos(2π·(52-w)/52), donc S30 et S22 sont
    # indiscernables. Le fichier est trié chronologiquement par département (2024-S01→S39,
    # puis la ligne 2023-S52) : on reconstruit la semaine par le rang, puis on vérifie le cosinus.
    df["week"] = df.groupby(["dept", "year"]).cumcount() + 1
    df.loc[df["year"] == 2023, "week"] = 52
    expected = np.cos(2 * np.pi * df["week"] / 52)
    if not np.allclose(expected, df["week_cos"], atol=1e-9):
        raise ValueError("Ordre des semaines incohérent avec week_cos")
    return df

// Regard critique

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Nowcasting : le modèle estime la semaine courante à partir de ses propres signaux ; ce n'est pas une prévision à J+7.
  • Seul, il ne bat pas la persistance S-1 sur 2024 (MAE 41,2 contre 39,5) ; la combinaison des deux est la piste d'amélioration, non validée.
  • 11 départements d'Auvergne-Rhône-Alpes seulement ; le département est une variable numérique (31,5 % du gain) : aucune généralisation possible à d'autres départements.
  • 39 semaines de test, dont 13 d'hiver : estimation de l'erreur hivernale fragile. Semaine encodée sans sinus : s et 52 − s sont indiscernables pour le modèle.
  • Aucune source de données citée et pas de données d'entraînement : réentraînement impossible, absence de 2024 dans l'entraînement probable mais non démontrable.
  • docker build non exécuté pendant la session (contenu de l'image testé dans un environnement vierge) ; Kubernetes validé par rendu seulement.
