Un copilote ERP qui cite ses sources et refuse d'inventer

Copilote pour directions financières sur ERP Sage / EBP : il cherche dans les procédures internes, interroge l'ERP en lecture seule et cite chaque affirmation. LLM open-weight sur GPU local via Ollama, chaîne native ou LangChain, banc LLMOps à deux juges, image Docker et manifestes Kubernetes.

// En 30 secondes

Le problème, la réponse, la preuve

Un DAF demande : « Un client a 70 jours de retard, garde-t-il sa remise ? » ou « Quelles factures dépassent 60 jours ? ». La réponse est à moitié dans les procédures et contrats, à moitié dans les données de gestion. Un chatbot générique y répond avec assurance et sans source, et invente au besoin un montant.

Ce copilote combine une recherche documentaire hybride et un outil SQL encadré. Il cite chaque phrase [S1] et refuse quand rien ne couvre la question. Le LLM tourne sur le GPU de l'entreprise, et chaque version est mesurée avant livraison.

Pour le recruteur · valeur business
  • Démarche LLMOps complète, documentée de bout en bout : mesurer, détecter une hallucination, en trouver la cause, corriger, vérifier.
  • Rigueur sur les chiffres : les montants et jours de retard viennent du SQL, jamais du modèle. C'est la condition de la confiance d'une direction financière.
  • Confidentialité : aucune donnée client ne sort du poste. Le même code bascule sur Azure OpenAI par simple variable.
  • Livré comme un produit : interface de chat, vitrine, vidéo, image Docker et déploiement Kubernetes expliqué pas à pas.
Pour l'équipe technique · ce que le code prouve
  • Recherche hybride BM25 + embeddings bge-m3 fusionnée par RRF : hit@5 100 %, MRR 0,92.
  • Text-to-SQL en lecture seule, à double verrou : validate_readonly_sql() (une instruction, tables en liste blanche) et un compte SELECT seul.
  • Deux chaînes de génération aux citations identiques : native et LangChain LCEL + ChatOllama, avec repli automatique.
  • Providers interchangeables par variable d'environnement : extractif (CI), Ollama (gemma4:e4b, qwen3.5:9b) ou Azure OpenAI.
  • Tokens réels journalisés à chaque appel (compteurs Ollama), avec coût, latence et rôle. Banc LLMOps à deux LLM juges de familles différentes.
  • Industrialisation : CI réparée sur un vrai SQL Server 2022, image Docker non root, kustomize (GPU local / AKS), Job d'ingestion, CronJob du banc.

// LLMOps

Mesurer, détecter, corriger, vérifier

1 · Mesurer, puis détecter
  • Premier banc : qwen3.5 à 4,8 / 5 de fidélité, gemma4 à 4,85.
  • Le juge repère 3 numéros de facture inventés sur « retards de plus de 60 jours » ; la métrique « citations valides » ne l'avait pas vu.
2 · Corriger à la source
  • La cause était l'outil SQL, pas le modèle : il renvoyait tous les impayés sans ancienneté.
  • Il calcule désormais les jours de retard en Python et filtre sur le seuil demandé.
3 · Vérifier
  • Nouveau banc : 5 / 5 pour tous les modèles, les deux juges d'accord.
  • Prochaine métrique : la complétude (gemma peut omettre 1 facture sur 8 sans rien inventer).

Étape par étape

  1. Découpage — procédures et contrats coupés en fragments de 800 caractères en respectant les sections, pour citer « Politique commerciale § 3 ».
  2. Embeddings — bge-m3 (1 024 dimensions, multilingue) servi par Ollama sur le GPU local.
  3. Recherche hybride — BM25 pour les termes exacts (numéros, TVA), vecteurs pour le sens, fusion RRF.
  4. Outil SQL — si la question porte sur des données, requête encadrée en lecture seule ; ancienneté des impayés calculée en Python.
  5. Génération ancrée — sources numérotées et consigne stricte : citer chaque affirmation, refuser sinon.
  6. Journalisation — rôle, modèle, tokens réels, coût, latence et sources de chaque appel, exposés sur /usage.
  7. Banc LLMOps — 13 questions (dont hors sujet et injection) × 4 configurations, notées par deux juges ; rejoué chaque nuit en CronJob.
// Points forts

Les points forts de la solution

  1. 01

    Zéro chiffre inventé : citations obligatoires, refus sans source, montants issus du SQL en lecture seule.

  2. 02

    Boucle LLMOps prouvée : une hallucination détectée par les juges, corrigée à la source, fidélité remontée à 5 / 5.

  3. 03

    Souverain et sans coût d'usage : LLM open-weight sur GPU local, même code vers Azure par variable.

  4. 04

    Prêt pour la production : CI sur SQL Server réel, image Docker, Kubernetes avec nœud GPU et moindre privilège.

// Extraits de code

Le code qui fait la différence

agents/safe_sql.py — premier verrou : une seule instruction, en lecture seule

statement = sql.strip().rstrip(";").strip()

if ";" in statement:
    raise SqlGuardError("Une seule instruction SQL est autorisée par requête.")

lowered = statement.lower()

first_token = next((t for t in _TOKEN_RE.findall(lowered) if t not in {"("}), "")
if first_token not in ALLOWED_START:
    raise SqlGuardError(
        f"Requête non autorisée : elle doit commencer par SELECT ou WITH (trouvé '{first_token}')."
    )

tokens = set(_TOKEN_RE.findall(lowered))
forbidden = sorted(tokens & FORBIDDEN_KEYWORDS)
if forbidden:
    raise SqlGuardError(f"Mot-clé interdit : {', '.join(forbidden)}.")

providers/llm.py — LLMOps : compteurs réels renvoyés par Ollama

def ollama_usage(data: dict) -> dict[str, float]:
    """Extrait les compteurs d'une réponse Ollama (durées en ns -> ms)."""
    eval_count = int(data.get("eval_count") or 0)
    eval_ms = (data.get("eval_duration") or 0) / 1e6
    return {
        "tokens_in": int(data.get("prompt_eval_count") or 0),
        "tokens_out": eval_count,
        "load_ms": round((data.get("load_duration") or 0) / 1e6, 1),
        "prompt_ms": round((data.get("prompt_eval_duration") or 0) / 1e6, 1),
        "eval_ms": round(eval_ms, 1),
        "tokens_per_s": round(eval_count / (eval_ms / 1000), 1) if eval_ms else 0.0,
    }

// Regard critique

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Banc de 13 questions : c'est un outil de non-régression, pas une étude statistique.
  • La fidélité ne mesure pas les oublis : une métrique de complétude est la prochaine étape.
  • Manifestes Kubernetes validés par rendu (kubectl kustomize) et image testée en conteneur, mais pas encore appliqués sur un cluster réel.
  • Authentification : oauth2-proxy (Entra ID) devant l'Ingress cloud ; le rôle métier doit encore être déduit des groupes Entra ID.
