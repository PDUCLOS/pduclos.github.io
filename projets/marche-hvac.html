Anticiper le marché des pompes à chaleur, département par département

Pipeline complet de l'open data à la prédiction : 5 collecteurs (ADEME DPE, Open-Meteo, INSEE, Eurostat, SITADEL), entrepôt en étoile, benchmark Ridge / LightGBM / Prophet / LSTM, API FastAPI, dashboard, Airflow et Kubernetes.

// En 30 secondes

Le problème, la réponse, la preuve

Pour un distributeur HVAC, savoir où et quand le marché des pompes à chaleur va accélérer conditionne stocks, force commerciale et partenariats installateurs. Les signaux existent (diagnostics énergétiques, permis de construire, météo, conjoncture) mais sont dispersés.

Le projet les réunit chaque mois dans un pipeline reproductible et restitue une prévision par département.

Pour le recruteur · valeur business
  • Sujet choisi dans mon secteur : les variables (MaPrimeRénov', CEE, type de logement) viennent de la connaissance terrain.
  • Livrable exploitable par une direction commerciale : carte de France, prévisions, comparaison de modèles.
  • Gouvernance documentée (RGPD, AI Act).
Pour l'équipe technique · ce que le code prouve
  • Collecteurs en architecture plugin (BaseCollector + registre), sans clé API.
  • Schéma en étoile SQLAlchemy (SQLite, PostgreSQL 16 ou SQL Server), détection d'outliers IQR / Z-score / Isolation Forest.
  • Split temporel train / validation / test + TimeSeriesSplit ; explicabilité SHAP.
  • FastAPI 6 endpoints, Streamlit 6 pages, Docker multi-stage non-root, DAG Airflow mensuel et CronJob Kubernetes équivalent.
  • CI : pytest 3.11 / 3.12 avec couverture, ruff, build + smoke test Docker.

Étape par étape

  1. Le 1er de chaque mois, Airflow (ou le CronJob Kubernetes) lance les collecteurs sur les 96 départements.
  2. Les données brutes sont nettoyées, fusionnées et chargées dans un schéma en étoile ; les valeurs aberrantes sont détectées par trois méthodes.
  3. Le feature engineering produit lags, moyennes et écarts glissants à 3 et 6 mois.
  4. Cinq familles de modèles sont entraînées sur un découpage temporel, puis expliquées avec SHAP.
  5. Les modèles sont servis par FastAPI et visualisés dans un dashboard Streamlit (carte de France, prévisions, comparatif).

Les points forts de la solution

  1. 01

    Connaissance terrain : variables choisies par le métier (MaPrimeRénov', CEE, type de logement).

  2. 02

    Prévision honnête : split temporel, TimeSeriesSplit, 5 familles de modèles comparées, explicabilité SHAP.

  3. 03

    Extensible : collecteurs en plugins, schéma en étoile portable (SQLite, PostgreSQL, SQL Server).

  4. 04

    Prêt à déployer : 562 tests, Docker non-root, DAG Airflow mensuel et CronJob Kubernetes équivalent.

// Extraits de code

Le code qui fait la différence

kubernetes/cronjob-pipeline.yaml — le DAG Airflow, version native Kubernetes

apiVersion: batch/v1
kind: CronJob
metadata:
  name: hvac-pipeline-monthly
spec:
  schedule: "0 6 1 * *"    # 1er du mois a 6h UTC
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 7200

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Audit post-projet : certaines moyennes glissantes incluent le mois courant de la cible, ce qui surestime les scores. Correctif identifié (décalage d'un mois) ; les métriques seront republiées après re-benchmark.
  • Pas de tracking MLflow ni de suivi de dérive : prochaine brique à ajouter.
