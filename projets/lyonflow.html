LyonFlow — la mobilité lyonnaise prédite en temps réel

Plateforme MLOps de bout en bout pour la mobilité lyonnaise : 9 sources open data, architecture Medallion sur PostgreSQL/PostGIS, 27 DAGs Airflow, XGBoost quantile (P10/P50/P90) à H+1h, suivi MLflow, dérive PSI, routage pgRouting et un dashboard à 3 personas. Déployée sur VPS ; cible Kubernetes rendue par kustomize.

// En 30 secondes

Le problème, la réponse, la preuve

La Métropole de Lyon publie des dizaines de flux ouverts (boucles de comptage, positions des bus TCL, stations Vélo'v, météo, chantiers), mais aucun outil ne les croise pour aider un usager à choisir son mode de transport, un opérateur à piloter son réseau ou un élu à arbitrer un investissement.

LyonFlow collecte ces flux toutes les 5 minutes, les raffine en couches Bronze → Silver → Gold, prédit trafic et disponibilité Vélo'v à H+1h, recommande le meilleur itinéraire multimodal et restitue le tout dans une application pensée pour trois publics.

Pour le recruteur · valeur business
  • Un produit en production, pas un notebook : déployé sur serveur, supervisé, sauvegardé chaque nuit.
  • Pensé pour 3 utilisateurs métier (usager, opérateur TCL, élu) — même logique que le pilotage commercial : chaque décideur a sa vue.
  • Le croisement retard bus × congestion distingue un problème opérationnel d'un besoin d'infrastructure (voie dédiée) : un argument chiffré pour un arbitrage budgétaire.
  • Projet porté seul de bout en bout : cadrage, données, modèles, déploiement, documentation RGPD.
Pour l'équipe technique · ce que le code prouve
  • Medallion Bronze/Silver/Gold sur PostgreSQL 16 + PostGIS + pgRouting, SQL paramétré partout, zéro credential en dur.
  • 27 DAGs Airflow (collecte 5 min → 6 h, transforms, ML, maintenance), archivage MinIO S3.
  • XGBoost quantile (P10/P50/P90) : vitesse entraînée chaque jour, Vélo'v chaque heure, inférence toutes les 15 min ; suivi MLflow avec repli sur un modèle local.
  • Dérive PSI maison (rapport quotidien), Evidently en option ; Prometheus + Grafana + Alertmanager, 7 groupes d'alertes.
  • CI GitHub Actions : ruff, mypy, bandit, pytest + couverture. Déploiement make deploy-vps / rollback-vps, Nginx seul point exposé.
  • Cible Kubernetes : kustomize base + overlays dev / prod + composant monitoring, rendu validé sans erreur.

// Revue

Ce que j'ai vérifié et corrigé

Vérifier les chiffres
  • 27 DAGs confirmés (28 appels DAG(...), dont 1 legacy).
  • Tests : 650 verts sur 674 collectés (et non 620), puis 653 avec 3 tests de sécurité ajoutés ; 0 échec.
  • « Retrain toutes les 30 min » était inexact : vitesse entraînée chaque jour à 03:38 (le DAG horaire est en pause depuis le 01/07/2026), Vélo'v chaque heure à :50 ; inférence toutes les 15 min.
  • 7 groupes d'alertes Prometheus confirmés (17 règles).
Corriger
  • Tests non portables sous Windows : lecture de fichiers sans encodage (UnicodeDecodeError), corrigée par encoding="utf-8".
  • Page « Statut du service » : base injoignable, elle affichait une trace Python complète. Le voyant Alertes et les derniers incidents suivent maintenant la règle des 3 autres voyants.
  • Rate limit contournable : l'API prenait la première IP de X-Forwarded-For, choisie par le client. Elle prend désormais la dernière, ajoutée par nginx.
  • Kubernetes : la base kustomize de la branche dormante ne se construisait plus. Réalignée sur main dans deploy/k8s ; UIs Prometheus / Alertmanager / Airflow protégées.

Étape par étape

  1. Collecte — 9 sources ouvertes, DAGs Airflow cadencés de 5 min (trafic, bus, Vélo'v) à 6 h (vigilance météo).
  2. Bronze — stockage brut JSONB immuable : on peut toujours rejouer l'historique.
  3. Silver — déduplication (DISTINCT ON), parsing SIRI, reprojection géographique (4326 / 2154), filtrage des capteurs défaillants.
  4. Gold — features ML (lags, moyennes glissantes, calendrier scolaire, météo) et vues matérialisées métier (goulots, retards par tronçon).
  5. Modélisation — XGBoost quantile vitesse H+1h (entraînement quotidien à 03:38, inférence toutes les 15 min), XGBoost Vélo'v H+1h (réentraînement horaire), routage voiture pgr_dijkstra.
  6. MLOps — suivi MLflow, comparaison aux données TomTom, rapport de dérive PSI quotidien (05:30) affiché aux personas. Le réentraînement est planifié, pas déclenché par la dérive.
  7. Restitution — API FastAPI (prédiction, itinéraire, goulots, RGPD) et dashboard Streamlit de 18 pages pour 3 personas.

Les points forts de la solution

  1. 01

  2. 02

  3. 03

src/monitoring/psi.py — dérive PSI robuste, sans dépendance lourde

def _safe_psi_term(pct_ref: float, pct_curr: float, eps: float = 1e-6) -> float:
    """Un terme de la somme PSI, protégé contre log(0) et division par 0."""
    if pct_ref < eps and pct_curr < eps:
        return 0.0
    if pct_curr < eps:
        pct_curr = eps
    if pct_ref < eps:
        pct_ref = eps
    return (pct_curr - pct_ref) * np.log(pct_curr / pct_ref)

dashboard/pages/Usager_5_Statut_Service.py — un voyant « Indéterminé » plutôt qu'une trace Python

def _kpi_alerts() -> dict | None:
    """KPI #4 — Alertes actives 6h.

    Comme les 3 autres voyants : si la base ne répond pas, le voyant passe
    en « Indéterminé » au lieu d'afficher une trace Python à l'usager.
    """
    try:
        df = cached_recent_alerts(hours=6, limit=50)
    except DashboardDataError:
        logger.warning("Statut service : alertes indisponibles (DB injoignable)")
        return None
    n_total = len(df)
    n_critical = int((df["severity"] == "critical").sum()) if "severity" in df.columns else 0
    return {"n_total": n_total, "n_critical": n_critical}

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Serveur unique : pas de haute disponibilité. La cible Kubernetes est rendue (kustomize) mais pas encore déployée : image à publier, MinIO, cert-manager, DAGs à valider sous KubernetesExecutor.
  • Le fonctionnement en production sur le VPS, le registre MLflow et toute métrique de précision n'ont pas été revérifiés lors de la mise à jour de cette fiche.
  • POST /api/v1/recommend renvoie encore un exemple codé en dur ; GET /api/v1/models affiche des métriques figées quand MLflow est injoignable.
  • Défauts d'interface non corrigés : balise </div> visible et texte tronqué sur l'accueil ; numéros de version incohérents (README, /health, OpenAPI).
  • Prédiction des retards bus encore en phase d'analyse : la donnée SIRI doit s'accumuler avant de passer en production.
  • Variante Databricks en cours : semaine 1 livrée (Unity Catalog, ingestion Bronze, DLT), MLflow / Model Serving / Genie à venir.
