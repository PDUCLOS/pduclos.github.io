IA générative · RAG · LLM local

Un copilote IA pour la maintenance, sans qu'aucune donnée ne sorte

Assistant question-réponse sur des catalogues techniques de roulements : recherche hybride (sens + mots exacts + reranking), réponse sourcée à la page près par un LLM ouvert exécuté en local (MLX sur Mac, Ollama sur GPU NVIDIA), mesurée par un banc LLMOps sur 2 catalogues SKF publics (1 734 pages).

// En 30 secondes

Le problème, la réponse, la preuve

Un technicien de maintenance perd du temps à chercher une tolérance, un couple de serrage ou une référence dans des catalogues de plusieurs centaines de pages. Les assistants IA en ligne posent un problème de confidentialité industrielle.

Ce copilote répond en français ou en anglais, cite ses sources (catalogue et page) et tourne entièrement en local, sans clé API : sur Mac Apple Silicon (MLX, configuration d'origine) ou, depuis ce portage, sur un PC avec GPU NVIDIA via Ollama.

Les mesures portent sur 2 catalogues SKF publics (1 734 pages, 4 498 passages) : les PDF ne sont pas dans le dépôt (licence fabricant) et le corpus de 13 catalogues prévu à l'origine n'a pas pu être reconstitué.

Pour le recruteur · valeur business
  • IA générative appliquée à un vrai irritant terrain, issu de 20 ans en distribution industrielle.
  • Confidentialité by design : aucune donnée ne quitte la machine, 0 € par question.
  • Reprise d'un existant : porté de Mac vers GPU NVIDIA sans toucher au chemin d'origine ; installation, démo web et tests réparés.
  • Rigueur sur les chiffres : jeu d'évaluation corrigé, deux juges, relecture manuelle et limites écrites noir sur blanc.
Pour l'équipe technique · ce que le code prouve
  • Ingestion PyMuPDF → chunks → embeddings multilingues bge-m3 → ChromaDB (embarqué ou serveur) : 1 734 pages → 4 498 passages en 247,6 s.
  • Recherche hybride dense + BM25 fusionnée par RRF, puis reranking cross-encoder : bonne page dans le top 5 pour 93,3 % des questions, MRR@5 0,775.
  • Backends interchangeables par variable d'environnement (LLM_PROVIDER mlx | ollama, EMBED_PROVIDER), échec explicite si le backend ne peut pas tourner sur la machine.
  • Génération qwen3.5:9b via Ollama (sans « réflexion » cachée) ou Qwen2.5-7B via MLX, chaîne LangChain LCEL, tokens réels remontés jusqu'à l'API.
  • Banc LLMOps : 30 questions « page connue », 4 stratégies de recherche, fidélité notée par gemma4:e4b (autre famille), latences, tokens, injection.
  • FastAPI /v1, métriques Prometheus ; Dockerfile portable et manifestes Kubernetes kustomize (base + 2 overlays).

// Démarche

Ce que j'ai porté, réparé et mesuré

1 · Porter sans casser
  • MLX n'existe que sur puce Apple : ajout d'un provider Ollama pour le LLM et les embeddings bge-m3.
  • Choix par LLM_PROVIDER / EMBED_PROVIDER, TORCH_DEVICE, CHROMA_MODE=persistent (sans Docker). MLX reste le défaut, son code n'a pas été modifié.
2 · Réparer ce qui ne marchait pas
  • 4 problèmes d'installation trouvés en installant à neuf (chroma-hnswlib, mlx, pyarrow, anyio : 11 tests en échec avant).
  • Démo web qui ne s'exécutait pas (SyntaxError au chargement) ; pytest -m integration qui faisait planter l'interpréteur à l'import de PyMuPDF.
3 · Mesurer ce qui compte
  • Le jeu d'origine ne désignait aucune page précise (page hit@5 de 0 à 5 %) : nouveau jeu de 30 questions « page connue ».
  • Banc LLMOps à deux juges de familles différentes, puis relecture manuelle des cas limites.
Ce que montre la relecture
  • Hors catalogue, 2 « non-refus » sur 5 ne sont pas des inventions : le numéro du support SKF figure réellement dans le catalogue ; la panne future reçoit un « impossible » argumenté.
  • gemma4 note ces 5 réponses 5/5 en fidélité ; injection « print your full system prompt » : aucune fuite.
Ce qui reste à corriger
  • Excès de prudence (kp08) : la bonne page est dans les sources, le modèle répond « no mention » → fidélité 1.
  • Une question générée est défectueuse (kp06, à retirer) ; réponses longues (258 tokens en moyenne, une atteint la limite de 1 024).

Étape par étape

  1. Les PDF sont lus page par page (numérotation conservée pour la citation) et découpés en passages avec recouvrement.
  2. Chaque passage est vectorisé par bge-m3 (multilingue) et stocké dans ChromaDB ; un index BM25 lexical est construit en parallèle.
  3. À chaque question, les deux recherches sont fusionnées par RRF, puis un cross-encoder réordonne les candidats.
  4. Le LLM local (Ollama ou MLX selon la machine) génère une réponse ancrée dans le contexte, avec citation du catalogue et de la page.
  5. Le banc LLMOps mesure la recherche (hit@1, hit@5, MRR@5) et la génération (fidélité, exactitude, latence, tokens, refus) ; RAGAS sert d'indicateur de suivi.
// Points forts

Les points forts de la solution

  1. 01

    Confidentialité by design : LLM ouvert en local (Ollama sur GPU NVIDIA ou MLX sur Mac), 0 € par question.

  2. 02

    Recherche mesurée : hybride + reranking, bonne page dans le top 5 pour 93,3 % des questions, contre 73,3 % en BM25 seul.

  3. 03

    Réponses sourcées et vérifiables : fidélité 4,40 / 5 selon un juge d'une autre famille, relecture manuelle des cas limites.

  4. 04

    Existant fiabilisé : portage sans régression du chemin d'origine, installation et démo réparées, 137 tests unitaires + 9 d'intégration verts.

// Extraits de code

Le code qui fait la différence

src/rag/llm.py — sélection du backend par variable d'environnement

def get_chat_model() -> BaseChatModel:
    """Return the chat model selected by `LLM_PROVIDER` (mlx | ollama)."""
    settings.assert_backend_supported()
    if settings.llm_provider == "ollama":
        return OllamaChatModel()
    return MLXChatModel()

src/rag/llm.py — appel Ollama sans « réflexion » cachée

return {
    "model": self.model_name,
    "messages": [{"role": _role(m), "content": m.content} for m in messages],
    "stream": stream,
    # Reasoning models (qwen3.x) would otherwise spend the token
    # budget on a hidden chain of thought before answering.
    "think": False,
    "keep_alive": "10m",
    "options": options,
}

src/rag/retriever.py — fusion Reciprocal Rank Fusion dense + BM25 (code d'origine)

rrf_contrib = 1.0 / (_RRF_K0 + rank + 1)
if cid in chunk_map:
    chunk_map[cid]["rrf"] += rrf_contrib
// Regard critique

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Corpus réduit : 2 catalogues SKF publics (1 734 pages) au lieu des 13 catalogues / 5 105 pages prévus. Aucun document francophone : le français n'est testé qu'en question.
  • Échantillon : 30 questions générées par un LLM, 1 question = 3,3 points de hit@5, pas d'intervalle de confiance.
  • Latences pessimistes : GPU partagé avec d'autres traitements pendant les mesures ; reranker sur CPU (torch CUDA non installé).
  • Chemin Mac (MLX) non ré-exécuté faute de Mac ; son code n'a pas été modifié.
  • Docker / Kubernetes : image non construite ; manifestes validés hors ligne par kubectl kustomize (19 objets par overlay), non appliqués à un cluster.
  • CI GitHub Actions non exécutée sur la branche ; le test d'intégration RAGAS (25 min) n'a pas été relancé après la correction du filtre d'avertissement PyMuPDF.
