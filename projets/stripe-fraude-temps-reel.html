Paiements : scorer la fraude en moins d'une seconde

// En 30 secondes

Le problème, la réponse, la preuve

Étude de cas de certification inspirée de Stripe, sur données synthétiques — sans lien avec l'entreprise.

Une plateforme de paiement doit bloquer une transaction frauduleuse avant de la valider, sans ralentir la base transactionnelle et sans que les analyses ne bloquent la production. Elle doit aussi respecter RGPD et PCI-DSS.

La réponse : séparer les usages. PostgreSQL pour la transaction, Debezium + Kafka pour diffuser les changements, Redis pour les features temps réel, MongoDB pour les journaux, Snowflake pour l'analytique — et un modèle surveillé qui se réentraîne quand la réalité change.

Pour le recruteur · valeur business
  • Sujet à fort enjeu financier : chaque fraude manquée coûte, chaque faux positif bloque un client.
  • Choix d'architecture justifiés et chiffrés, y compris le coût cloud (FinOps) : ~3 100 $/mois en prod, ramenés à ~2 400 $ avec les leviers identifiés.
  • Conformité intégrée dès la conception : aucun numéro de carte stocké, empreintes SHA-256, rétention limitée des journaux.
  • Incidents réels documentés et résolus — la preuve d'une posture d'exploitation, pas seulement de développement.
Pour l'équipe technique · ce que le code prouve
  • CDC Debezium sur le WAL PostgreSQL → Kafka (KRaft), write-back idempotent du score.
  • Feature store Redis (vélocité 1 h / 24 h en sorted sets) et même vecteur de features à l'entraînement et à l'inférence : zéro training/serving skew.
  • Split temporel anti-fuite, XGBoost avec scale_pos_weight, MLflow registry fraud-detector.
  • Moniteur Evidently : réentraînement automatique si dérive > 0,3, rappel < 0,7 ou précision < 0,5, avec délai de carence.
  • CI qui monte toute la stack sans mock + notebook d'audit exécuté comme porte qualité ; Terraform AWS (VPC 3 AZ, RDS, MSK, ElastiCache, ECS Fargate, MWAA).

Étape par étape

  1. Un producteur insère des transactions synthétiques (5 % de fraude injectée) dans PostgreSQL 16, configuré en réplication logique.
  2. Debezium lit le journal WAL et publie chaque changement dans Kafka (stripe.public.transactions).
  3. Le scorer enrichit chaque transaction avec les vélocités client stockées dans Redis, puis la note (règles ou XGBoost) : autoriser, revoir (≥ 0,60) ou bloquer (≥ 0,85).
  4. Le score est réécrit de façon idempotente dans PostgreSQL ; les événements et alertes partent dans Kafka puis MongoDB.
  5. Le moniteur compare toutes les 2 minutes les données récentes à la référence (Evidently) et la performance réellement servie ; il relance l'entraînement si nécessaire.
  6. Chaque nuit, Airflow exporte vers le modèle en étoile Snowflake et rafraîchit les vues matérialisées.
  7. Le dashboard Streamlit (authentifié) expose KPIs, alertes, dérive et comparaison règles / modèle.
// Points forts

Les points forts de la solution

  1. 01

    Temps réel de bout en bout : CDC Debezium → Kafka → scoring (cible sous la seconde), score réécrit de façon idempotente.

  2. 02

    Zéro training / serving skew : feature store Redis et même vecteur de features à l'entraînement et à l'inférence.

  3. 03

    Modèle qui se surveille seul : réentraînement automatique sur dérive ou baisse de rappel / précision, avec délai de carence.

  4. 04

    Architecture chiffrée et conforme : 9 modules Terraform AWS, FinOps ~3 100 → ~2 400 $/mois, aucun numéro de carte stocké.

ml/train_fraud_model.py — split temporel pour éviter la fuite d'information

def temporal_train_test_split(df, X, y, test_frac=0.2):
    """Split train/test par ordre chronologique (pas aléatoire).
    Un split aléatoire mélangerait les fenêtres de vélocité passé/futur :
    le modèle "verrait" indirectement des transactions futures."""
    n = len(df)
    cut = int(n * (1 - test_frac))
    return X[:cut], X[cut:], y[:cut], y[cut:]
// Regard critique

Limites connues et prochaines étapes

Documenter honnêtement les limites fait partie du travail : c'est ce qui permet à une équipe de décider en connaissance de cause.

  • Flink remplacé par un consommateur Python équivalent (PyFlink ne compile pas sur ARM64) ; le job PyFlink existe en profil optionnel.
  • Snowflake exécuté en dry-run faute de compte ; Terraform validé mais jamais appliqué.
  • Pas encore de porte de promotion ni de rollback automatique dans le registry MLflow.
  • Écart offline / online observé sur une fenêtre (précision servie 0,52) : signalé par le notebook d'audit lui-même, piste de calibration.
